# Mollusk tests

Instruction-level tests of `cross_core` against the built binary (`target/deploy/cross_core.so`): one instruction, hand-built accounts, and a check of exactly what changed, which error came back and how many compute units it took. The LiteSVM suites in `tests/core` run whole flows; these are for a single instruction's contract.

```
cargo +nightly test            # from tests/mollusk, after `anchor build` (or cargo build-sbf) has produced target/deploy/cross_core.so
cargo +nightly test -- --nocapture   # also prints the compute units of init_protocol, set_paused and an unknown instruction
```

Why nightly and why a separate workspace: `mollusk-svm 0.16.2` pulls `solana-program-runtime 4.3.x`, which needs a compiler newer than the repository's pin (1.96.1). The crate is its own workspace (`[workspace]` in `Cargo.toml`) so the programs keep building with the pin. Verified in WSL with the current nightly; 37 tests pass across four suites.

What they pin, by suite:

- `tests/cross_core.rs` (11 tests): the admin instructions of `cross_core`. The Anchor discriminators, `init_protocol` writing exactly the given fields into a 147-byte account the admin pays for, the 100 bps fee cap on all four slots, no second init, `set_paused` by guardian or admin and by no one else (and only a key that signed), the protocol PDA seed constraint, `set_guardian` and `set_protocol_fees` being the admin's alone, the two-step admin handover, and the unknown-instruction error.
- `tests/idl_surface.rs` (5 tests): the whole surface of 12 deployed binaries from their IDLs. All 327 instruction, account and event discriminators are what Anchor derives from the names (four interface instructions of `cross_gate` use their interface's own, named in the test); each of the 169 instructions the binaries route reaches its handler and refuses an empty call; an unknown discriminator, an account discriminator and a call under eight bytes are refused as "no such instruction"; each binary refuses to run at any address but the one its IDL names; instruction names and error numbers are unique. **A finding, found and closed:** `target/deploy/cross_gate.so` (built 2026-10-11) was older than `cross_gate`'s IDL and routed 17 of its 34 instructions; the test pinned the list. The binary was rebuilt on 2026-10-16 (667,064 bytes, sha256 `76bf9119da252d424f497849bc46a84bc2cd51f7717290b0e06d453c5183a604`, the same hash the gate work produced independently) and now routes all 34, so the list is empty. The mechanism stays: an IDL that runs ahead of its binary fails the test until the binary is rebuilt.
- `tests/backing.rs` (8 tests): `cross_backing` with a real call into `cross_core`. The protocol and the halt state are made by `cross_core`'s own instructions, not written by hand. Policy terms and who may opt an asset in; the attester and the chain's clock; `check` halting through `cross_core`'s `set_halt` when backing is missing, stale or short, refusing with `Backed` (and changing nothing) when it covers the live supply; coverage and age exact at their boundaries; substituted accounts refused.
- `tests/core_halt.rs` (13 tests): who may register a halt state and who may halt; the first halt reason standing; corporate actions; a paused Token-2022 mint (built byte for byte with the pausable extension) copied in by anyone; the oracle circuit breaker on hand-built Pyth `PriceUpdateV2` accounts: first update recorded, a 5.00% move not tripping and 5.0095% tripping, a move in either direction, outside the window, across exponents, and every kind of update it must refuse (another feed, partially verified, not from a Pyth receiver, older than 120 seconds, a zero or negative price, malformed, replayed or older than the last).

Run `cargo +nightly test -- --nocapture` to see the compute units each instruction took.

Not covered here: the order, clearing, claim and settlement instructions of `cross_core` (they need token accounts and the cross state machine; `tests/core` and `tests/surfpool` cover them end to end), `cross_gate` beyond routing (its instructions run end to end on LiteSVM in `packages/cross-gate-client/test/svm`), `cross_settle`, `treasury`, `cross_mandate`, `cross_conviction`, `cross_basket`, `cross_listing`, `cross_bounty` and `cross_graduate` beyond routing, and `cross_calendar` beyond routing (`tests/surfpool` drives it end to end). No mutation test of these suites has been run. Build and run them in WSL with `CARGO_TARGET_DIR` outside the repository, and delete the target directory afterwards.
