# @opening-cross/diagnose

Explains why a Solana transaction failed, in plain words, from the programs' own error tables.

```ts
import { diagnose, diagnoseSignature, fromKitError } from '@opening-cross/diagnose';

const d = diagnose({ err, logs });           // from a status's err and the transaction's log messages
const r = await diagnoseSignature(rpc, sig); // any client with call(method, params)
const k = fromKitError(thrownKitError);      // then diagnose(k)

d.summary;  // "Meteora Dynamic Bonding Curve refused the transaction while running Swap2: ExceededSlippage (Exceeded slippage tolerance)."
d.category; // slippage | balance | account | authority | compute | blockhash | state | math | program-rule | network | unknown
d.advice;   // what to do, ending with: a failed transaction changed nothing but the network fee
```

The tables (`src/tables.generated.ts`) are generated by `pnpm --filter @opening-cross/diagnose generate` from the IDLs in the repository, Anchor's error enum and the SPL clients; nothing is typed by hand. The innermost failing program is blamed, and when the program also logged its own error name the two are compared: a disagreement means the IDL on file is older than the deployed program, and the diagnosis says so. Against real mainnet failures (`scripts/mainnet-check.ts <program>`), 69 of 69 failures inside Meteora DBC, DAMM v2, DLMM and Raydium CPMM matched the program's own log. An error it cannot place is reported as unmapped with the evidence, never guessed.

Evidence: `docs/evidence/W2A-L5-diagnose.md`; decision: `docs/adr/0303-failure-diagnosis-from-sources-of-truth.md`.
