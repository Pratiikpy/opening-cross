# W2A-L5: transaction failure diagnosis (`packages/diagnose`)

Date: 2026-10-13. Row L5: "DBC/DAMM developer reliability layer: diagnoses slippage failures, Kit-compatible SDK, version-matched docs."

## What was built

`@opening-cross/diagnose` turns a failed transaction (its error and logs, or its signature) into a plain account of what failed, where, and what to do. Error words come from tables generated by `pnpm --filter @opening-cross/diagnose generate` from the sources of truth, never typed by hand: the IDLs in `idls/` (Meteora DBC 0.2.1, DAMM v2 0.2.5, DLMM 0.12.0, Met Lock, Zap, Raydium CPMM 0.2.0) and the Opening Cross programs' own client IDLs, Anchor's framework error enum (82 errors, codes 100 to 5000, each checked against its doc-comment number), and the generated error files of the SPL Token, Token-2022, System and Associated Token clients. `diagnose()` finds the innermost failing program from the logs (so a router that calls a pool names the pool), reads its own `AnchorError` log line, looks the code up, and compares the table with what the program logged. Disagreement means the deployed program is newer than the IDL on file, and the diagnosis says so and trusts the program. It accepts a `@solana/kit` error (`fromKitError`), a signature (`diagnoseSignature`, with any client that has `call()`), or plain `err` and `logs`. Every diagnosis states that the failed transaction changed nothing but the fee.

## Tests

23 unit tests (`pnpm exec vitest run`; `tsc` clean): a slippage failure on a bonding curve; a router calling a pool; no logs; a stale table; Anchor framework codes; a program with no table that logged its own error; an unmapped code; token errors; this protocol's errors; compute budget; stale blockhash, duplicate, empty fee payer; input it cannot understand; the tables against the IDL files; signature lookup; kit errors.

## Against real mainnet failures (read-only)

`scripts/mainnet-check.ts <program>` takes recent failed transactions of a program and compares the diagnosis with what the program logged ("Error Code: X. Error Number: N"), which is ground truth. For each program it kept going until it had seen failures inside that program itself, or spent its fetch budget:

| Program | Failures that failed inside it | Table agreed with the program's own log | Disagreed |
|---|---|---|---|
| Meteora DBC | 19 | 19 | 0 |
| Meteora DAMM v2 | 39 | 39 | 0 |
| Meteora DLMM | 1 | 1 | 0 |
| Raydium CPMM | 10 | 10 | 0 |

The failures were `ExceededSlippage` (16 of the first 80 DBC failures sampled), `ConstraintTokenMint` and `ExceededSlippage` on DAMM v2, all mapped to the right name, message and category. The rest of the failed transactions that reference these programs failed in other programs in the same transaction (token program `NonNativeHasBalance`, Jupiter 6001, aggregator and bot programs); those were diagnosed from the logs the program wrote, or reported as unmapped when it wrote none (Jupiter 6001, and several unlisted programs), never guessed.

A finding from this run: of the 2,000 most recent transactions that reference the DBC program, 615 (30.8%) failed, but only 19 of the 80 failures diagnosed (24%) failed inside DBC itself; the others failed in another program in the same transaction. A raw failure rate for transactions that merely reference a program therefore overstates how often the program fails. The "17% of DBC transactions fail" figure in the feature text was not reproduced and is not claimed here.

Two things found and fixed: mainnet now serves version-1 transactions, so lookups need `maxSupportedTransactionVersion: 1`; and `TooLittleOutputReceived`, `MinReturnNotReached` and `InsufficientOutAmount` (what other swap programs call slippage) were first categorised as generic program rules, now as slippage.

## Not covered

DAMM and DBC were checked on mainnet only; no devnet failure of a Meteora program was produced. DLMM had one failure of its own in 240 diagnosed, so its agreement is one data point. The "version-matched docs" half of the row is not built: the diagnosis names the IDL version its table came from but links to no documentation. A Kit-compatible SDK means `fromKitError` and a `call()`-shaped client; it was exercised against a hand-built kit error shape, not a live kit exception. Only the programs listed are mapped; any other program's custom code is explained only if it logs an Anchor error.
