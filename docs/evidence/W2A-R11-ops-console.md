# W2A-R11: the operations console API (`services/ops`)

Date: 2026-10-13. Code: `services/ops` (auth, hash-chained log, routes, evidence gathering, `main.ts`), migration `014_ops.sql`. Tests: 13 (`test/ops.test.ts`, against Postgres 18), `tsc` clean. Decision: ADR-0305.

## What it does

A token-authenticated API (`Authorization: Bearer ...`; the server holds only each token's sha-256, compared in constant time) with three roles. **Listing queue:** a reviewer opens a review of a mint or a cross, the console gathers evidence at that moment (safety, authenticity, duplicates, holders, supply, backing; or the cross, its proof, conflicts, organic volume and rating), and a different person decides: approve, reject or ask for more, with a written reason of at least ten characters; an approval on evidence that could not be gathered needs the explicit flag, and that acknowledgement goes in the log. **Incidents:** opened by hand or by the monitor's webhook (a pause by the monitor, a failed pause, a critical finding that has persisted), de-duplicated while open, acknowledged by a reviewer, resolved by an admin with a resolution. **Cases:** sanctions, fraud, support or other, about a wallet, cross or mint; notes are append-only and by name; closing is an admin's. **Audit log:** every action above is one entry in a hash chain (each entry's hash covers the previous one), written in the same transaction as the change it records; `GET /v1/ops/log/verify` recomputes the chain and names the first broken entry; `GET /v1/ops/log/head` returns the head signed by the operator key.

## Tests

Role checks (a viewer cannot open a case, a reviewer cannot resolve an incident or verify the log); no tokens configured means every request is refused with a message saying so; a listing cannot be decided by the person who opened it, a short reason is refused, an unknown decision is refused, an already decided review cannot be changed, evidence failure blocks approval until acknowledged and the acknowledgement is in the log; the monitor webhook (wrong secret 401, malformed event 400, an incident event, a failed pause and a persisted critical finding open incidents, a warning and a first-pass critical finding do not, a repeat does not open a second, a resolved incident can be opened again); case notes by two reviewers in order, twelve notes read back in order, a note's text is not copied into the log, a reviewer cannot close; the chain links each entry to the one before, an edited entry is found (`its content does not match its hash`) and a removed one is found (`removed or inserted`), a broken chain is never signed, and the signed head verifies; 24 concurrent actions produce one valid chain.

**A defect the concurrency test found:** `verifyChain` and the log reader selected `seq::text AS seq` and ordered by `seq`, which Postgres resolved to the text output, so entries sorted 1, 10, 11, ..., 2 and a correct chain of more than nine entries was reported broken. Fixed by ordering on the table's own column; the same pattern in the case notes, listings, incidents, cases, billing payments and invoices was corrected too (twelve notes are now a test). The disaster-recovery restore also had to reset serial sequences after loading rows with their own `seq`; a test inserts after a restore.

## Not covered

No web console: this is the API a console would call. Real people and tokens: none issued (HUMAN_TASKS). The hash chain proves the log was not altered by someone who cannot also rewrite every later row and the signed head; it does not stop the database owner, who holds the signing key, from re-signing a rewritten chain, so a head must be copied somewhere the operator cannot quietly change (the point of publishing it). Rate limiting and lockout of the console API are not built. Fraud review is a pack of the existing integrity evidence; cases have notes and a closing, not an assignment or a due date (the table has an `assignee` column that no route sets).
