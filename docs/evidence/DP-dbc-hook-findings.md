# Findings from the DBC continuation proof

Companion to `DP-dbc-hook.md` (that file is regenerated by each run).

1. **The DBC SDK cannot resolve owner-dependent hook accounts.** `getRemainingAccountsForTransferHook` (SDK 1.5.13) resolves extra accounts against `PublicKey.default` source and destination, so any hook whose extra accounts are seeded from token-account data (ours: pass and lock PDAs keyed by owner) throws `TokenTransferHookInvalidSeed`. The DBC *program* accepts correctly resolved accounts; the proof resolves them against the real vault and wallet. Our adapter does the same, and the fix is worth proposing upstream.
2. **DBC removes the transfer hook when the curve completes** (`process_swap.rs` `revoke_transfer_hook`; observed on devnet: the hook program becomes the null address). Passes and locks stop being enforced at graduation, although lock records remain. Gating and lockups that must outlive the curve need Token ACL (DP8) or escrow-held vesting; a hook lock is never presented as a post-graduation guarantee.
3. **DBC mints cannot adopt Token ACL later.** A DBC-created Token-2022 mint has no freeze authority and no Default Account State extension (observed with `spl-token display`), and both can only be set when a mint is created. Token ACL is therefore usable only for mints we create ourselves.
4. **Mint authority is usable before trading and revocable.** Minting 5M tokens to a winner left DBC's base reserve, vault and price unchanged, and a fixed-supply config still migrated and released its leftover — the continuation design (clear the cross, mint Q* at P*, revoke, let the curve run) holds.
