# Opening a market, Meteora's programs, issuer neutrality and the keeper's duties

Workstream W3E. This is the reference for the routes and keeper actions that finish the layer W3A left as SDK-only (`W3A-rules-treasury-settle.md`), for the screens
built on them. Everything here is built and tested against fixtures, the generated clients and real Solana devnet accounts. **The instructions of the extended
programs are not on devnet until the operations key is funded (docs/HUMAN_TASKS.md H27)**: a route answers 409 `PROGRAM_NOT_DEPLOYED` instead of a
transaction the deployed program would refuse, and `GET /v1/programs` reports the release.

## Conventions (additions to W3A)

- A transaction route answers `{ transaction, signers, bytes, ...facts }`, or `{ transactions: [{ transaction, signers }], sizes, atomic, ...facts }` where a step may need more than one transaction (send them in order, each after the one before has landed). `bytes` / `sizes` are the wire sizes; every transaction was measured against the 1,232-byte limit before it was handed out (422 `TX_TOO_LARGE` with `bytes`, `limit` otherwise).
- The heavy instructions start with a compute-budget instruction of 1,400,000 units (the limit tests/core proves them with). The same is now true of every `cross_settle` route in `settle-tx.ts`.
- `release: { program, instruction, deployed }` is on every `cross_settle` answer. `deployed: true`: the instruction was found in the program's bytes. `deployed: null`: the program could not be read, or a control instruction every release has was not found, so the scan is not trusted. An unreadable program is never reported as an old one.
- 409 `PROGRAM_NOT_DEPLOYED { program, instruction }`: the program was read and the instruction is not there. 409 `EXTERNAL_PROGRAM_MISSING { program, name }`: a Meteora program the route builds for does not exist on this cluster.
- A fresh keypair that must sign (`base`, `vesting`, `limitOrder`) is generated by the caller; the route names it in `signers`.
- Amounts of liquidity are u128 decimal strings; token amounts u64 decimal strings.

## Opening a market (`routes/settle-open-tx.ts`)

All of these answer 422 `NOT_THE_CREATOR` unless `creator` is the cross's creator, 409 `LIVE` / `NOT_CLEARED` unless the cross printed a price, and (except `open-dbc-pool`) 409 `NO_BASE_MINT` until the base mint is bound.

| Route | Body | Answer / notes |
|---|---|---|
| `POST /v1/tx/open-dbc-pool` | `{ cross, creator, design, name, symbol, uri, locked? }` | `{ cross, transactions, sizes, atomic, locked, clearingPrice, pool, config, baseMint, designIssues, warnings, release }`. The DBC config and pool at the clearing price, then the mint bound. One atomic transaction when it fits (1,119 bytes for a two-segment curve; eight segments need two), otherwise open then bind. `locked` defaults to true (`open_dbc_pool_locked`). `design` is JSON: `token, fee, migration, liquidityDistribution, lockedVesting, activationType, sqrtPriceMultiples`, optional `liquidityWeights` and `volatilityFee`; every enum is a number. 422 `DESIGN_NOT_LOCKED { issues }` names every departure from the locked, compounding design; 422 `DESIGN_INVALID`; 422 `WRONG_SETTLER` (not a deferred-mint cross for this adapter); 409 `ALREADY_BOUND`, `POOL_EXISTS`. Both variants need the build that has `open_dbc_pool_locked`: an older program has the same `open_dbc_pool` name with the older argument layout. |
| `POST /v1/tx/bind-dbc-mint` | `{ cross, payer }` | The second step alone. 409 `POOL_NOT_OPENED` until the base mint exists with the settler as its mint authority; 409 `ALREADY_BOUND`. |
| `POST /v1/tx/seed-damm-v2` | `{ cross, creator, baseAmount, quoteAmount, feeBps, collectFeeMode?, compoundingFeeBps?, batch?, alphaVault?, lock? }` | A DAMM v2 pool at exactly the clearing price. `batch: { windowSecs, activationPoint, endingFeeBps, periods, periodSecs }` opens it closed for a batch window (`seed_damm_v2_batched`); the answer carries `landBy` (the last second the program accepts the start). `alphaVault: true` needs a `batch`. `lock: { permanentLiquidity?: "all" or u128, vest?: { vesting, cliffPoint, periodFrequency, cliffUnlockLiquidity?, liquidityPerPeriod, numberOfPeriod } }` locks liquidity from the first block, in the same transaction when it fits. Answers `{ transactions, sizes, atomic, pool, position, positionNftMint, liquidity, release }`. 422 `BATCH_INVALID { issues: [{ code, field, message }] }` (codes are the program's `BatchWindow`, `BatchActivation`, `BatchFeeNotDecaying`), `BatchNotCompounding`, `ALPHA_NEEDS_BATCH`, `LOCK_OVER_LIQUIDITY`, `INSUFFICIENT_BASE` / `_QUOTE`; 409 `NO_BASE_ACCOUNT` / `NO_QUOTE_ACCOUNT { account }`, `POOL_EXISTS`. |
| `POST /v1/tx/open-dlmm-pair` | `{ cross, creator, binStep, baseFactor, baseFeePowerFactor?, batch?: { windowSecs, activationPoint, alphaVault? }, badges?: { base?, quote? } }` | A DLMM pair whose active bin holds the clearing price: `open_dlmm_pair`, `_batched`, or `_badged` (Token Badges for tokenized stocks, the two badge accounts appended base then quote). `{ transaction, signers, bytes, lbPair, activeId, landBy?, release }`. 422 `BADGE_MISSING { role, mint, badge }` (the badge account must exist and belong to DLMM), `NO_BIN_FOR_PRICE`, `BATCH_INVALID`; 409 `POOL_EXISTS`. |
| `POST /v1/tx/seed-raydium-cpmm` | `{ cross, creator, baseAmount, ammConfigIndex?, openTime? }` | The quote amount is derived from the clearing price. `{ transaction, signers, bytes, pool, quoteAmount, release }`. 422 `AMOUNT_TOO_SMALL`. Devnet or mainnet addresses follow the API's network. |
| `GET /v1/crosses/:address/venues` | | `{ cross, state, creator, clearingPrice, baseBound, deferredMintWithSettler, venues: { dbc, dammV2, dlmm, raydiumCpmm }, available: ["open-dbc-pool" \| "bind-dbc-mint" \| "seed-damm-v2" \| "open-dlmm-pair" \| "seed-raydium-cpmm"], note }`. Each venue is `{ addresses..., opened }`, null until the base mint exists (the DBC entry exists for a deferred-mint cross with the settler). The screen shows `available`. |

The payouts and the greenshoe (`settle-tx.ts`) now also carry the release check, the compute limit and the size check.

## Meteora's Alpha Vault, Met Lock and Dynamic Fee Sharing (`routes/meteora-tx.ts`)

These are Meteora's programs, so the check is that the program exists on the cluster. Their accounts are decoded from their IDLs; the decoders were checked against 16 real devnet accounts (PDA of every vault and escrow re-derived from the fields read) and the fee vault of `docs/evidence/D7-fee-sharing-vault-devnet.md`.

### Alpha Vault (DAMM v2 pools; keyed by the cross whose pool it binds)

| Route | Body | Notes |
|---|---|---|
| `POST /v1/tx/alpha-vault-init` | `{ cross, funder?, mode: "prorata" \| "fcfs", maxBuyingCap \| maxDepositingCap + individualDepositingCap, startVestingPoint, endVestingPoint, depositingPoint?, escrowFee?, whitelistMode? }` | The cross creator signs as the vault base (DAMM v2 records only that vault); `funder` defaults to the creator. 409 `NO_POOL` (seed the pool with `alphaVault: true` first), `VAULT_EXISTS`; 422 `VESTING_ORDER`. |
| `POST /v1/tx/alpha-vault-deposit` | `{ cross, owner, amount, payer? }` | Opens the owner's escrow on a first deposit (`opensEscrow`, `escrowFeeLamports`). 422 `OVER_CAP { room }`, `INSUFFICIENT_QUOTE`; 404 `NO_ALPHA_VAULT`. |
| `POST /v1/tx/alpha-vault-fill` | `{ cross, cranker, maxAmount? }` | Anyone. Default `maxAmount` is what the vault may still spend (deposits, capped by a pro-rata vault's buying cap, less what it spent). 409 `NOTHING_TO_FILL`; 422 `OVER_FILL { left }`. |

### Dynamic Fee Sharing

`cross` names the cross whose quote token is split; or name `mint` (its token program is read from the mint). One of them is required, not both.

| Route | Body | Notes |
|---|---|---|
| `POST /v1/tx/fee-share-create` | `{ payer, base, owner?, cross \| mint, recipients: [{ address, share }] }` | 1 to 5 distinct recipients, `share` a positive integer weight; `base` is a fresh keypair. Answers each recipient's `percent`. |
| `POST /v1/tx/fee-share-fund` | `{ funder, base, cross \| mint, amount }` | 404 `NO_FEE_VAULT`; 422 `INSUFFICIENT_TOKEN`. |
| `POST /v1/tx/fee-share-claim` | `{ user, base, cross \| mint, index }` | Creates the claimer's token account when missing. 422 `NOT_THE_RECIPIENT { recipients }`. |
| `POST /v1/tx/fee-share-transfer-position` | `{ cross, owner, base }` | Hands the cross's DAMM v2 position to the vault. **One way.** Refused unless the vault exists, splits this pool's quote token (422 `VAULT_TOKEN_MISMATCH`) and the creator holds the position (409 `NOT_THE_HOLDER`, `ALREADY_IN_VAULT`). The answer carries a `warning` and the recipients. |
| `POST /v1/tx/fee-share-fund-from-damm` | `{ cross, signer, base }` | The signer must be a recipient (422 `NOT_A_RECIPIENT`) and the position must be in the vault (409 `POSITION_NOT_IN_VAULT`). |
| `GET /v1/fee-share/:base/:mint` | | `{ feeVault, tokenVault, vault, shares }`; `vault` null with a note when none exists. |

**The DBC creator and partner trading-fee bridges are not built, and cannot be offered for a pool this protocol opens** (ADR-0701). Meteora's fee-sharing program claims a DBC pool's fees only when the vault *is* the pool's creator or fee claimer. A pool opened by `cross_settle` has the issuer's wallet as creator and the settler PDA as fee claimer (`open_pool`: `fee_claimer: a.settler`), and the fee claimer is fixed in the config. The partner's fees already reach the fee recipient through `claim-partner-fee`. The creator side could only be moved to a vault with DBC's `transfer_pool_creator`, which also moves the creator's migration liquidity (`migrate_damm_v2_initialize_pool` mints the creator's position to `virtual_pool.creator`) to an account that can sign nothing: the 10% locked and 60% vesting share of the locked design would be stranded. The bridge for a DAMM v2 position's fees (`fee-share-transfer-position`, `fee-share-fund-from-damm`) is built and is the route fees take after migration.

## Issuer neutrality (`routes/challenges.ts`, and checks added to `routes/rules-tx.ts`)

| Route | Answer |
|---|---|
| `GET /v1/arbiter` | `{ registry, arbiter, named, deadlineSecs }`; `named: false` with a note (HUMAN_TASKS H28) until the protocol admin names one. |
| `GET /v1/crosses/:address/challenge-state` | `{ cross, applies, state, insiders, bond: { posted, held, slashed }, window: { clearedAt, closesAt, open }, filed, open, challenges: [{ id, address, challenger, subject, evidence, deposit, filedTs, expirableAt, expirable }], arbiter, arbiterNamed, arbiterDeadlineSecs, depositLamports, finalizeBlocked: "open challenges" \| "challenge window" \| null }`. Read from chain: a challenge account is closed when ruled on or expired, so only open ones are listed; `GET /v1/crosses/:address/challenges` (the index) has every outcome. |

Checks now made before a transaction is handed out: `challenge-insider` 409 `WINDOW_CLOSED { closesAt }` and 422 `ALREADY_DECLARED`; `resolve-challenge` 409 `NO_ARBITER` and 422 `NOT_THE_ARBITER { arbiter }`; `expire-challenge` 409 `DEADLINE_NOT_REACHED { expirableAt, filedTs }` (14 days after filing). `spawn-next` now makes the program's own checks: 409 `SPAWN_TOO_EARLY { openTs, spawnableAt }`, `PREVIOUS_LIVE`, `PREVIOUS_MISSING`, `NO_SESSION_AHEAD`, and answers `closeTs`, `openTs`; the spawned cross has no shards, so send `init-shards` for it. `POST /v1/treasuries/:address/tx/redeem` answers 409 `WOUND_DOWN` after the sweep.

## The keeper (`services/keeper`, ADR-0703)

A pass reads every account it acts on from chain. The lifecycle of a cross (settle, draw, abandon, claim, finalize) is unchanged. The duties below are named in `KEEPER_DUTIES` (a keeper built before them does none):

| Duty | Action | When | Idempotent because |
|---|---|---|---|
| `refunds` | `push-refunds` | A cross with a rules tail has two or more orders that can only be refunded (a no-print cross, an order never revealed, a buy under the clearing price, a sell over it): up to 12 per transaction. The rest are claimed. A cross without a tail, and the orders at the price itself, are always claimed. | Closed orders are gone from the next read. A batch the program refuses falls back to claims in the same pass and is not tried again for an hour (with memory). |
| `challenges` | `expire-challenge` | An open challenge is 14 days old. `finalize` of a cross with a bond is held back, with the reason, while a challenge is open or the window runs. | The challenge account is closed. |
| `locks` | `release-locked` | A lockup has at least `KEEPER_MIN_RELEASE` vested unreleased atoms, or what is left is all that remains. | `released` moves; the last release closes the account. |
| `series` | `spawn-next`, then the new cross's missing shards | `spawn_next` would be accepted (series active, previous cross resolved, the next close within a day of its call opening, on an interval or the calendar's next session). | The series' `next_index` and `last_cross` move; the new cross is live, so the series waits. |
| `halts` | `sync-pause`, `observe-price` | The base mint is paused and the halt state is not halted; the pause was lifted (marks `issuer_unpaused`, which tells the authority a resume cross is due); a breaker has a verified, newer, younger-than-90-seconds update. The halt state is never lifted by the keeper: only a printing resume cross does. | The halt state records both. |

Run before the crosses, `halts` puts a pause into the halt state before a cross that names it is cleared; `clear` is given the halt state (and a flagged corporate action) by `buildSettleBook` and prints no price while the asset is halted.

Environment: `KEEPER_DUTIES` (`default` = refunds, challenges, halts; `all`; `none`; or a comma list), `KEEPER_DRY_RUN=1` (plan everything, send nothing; the pass logs `planned`), `KEEPER_MIN_RELEASE` (base atoms, default 1), `KEEPER_BREAKER_FEEDS` (hex Pyth feed ids whose push-oracle account may be fed to a breaker). `locks` pays for an owner's token account on a first release and `series` pays the rent of every cross it spawns, which the program does not return: both are done only when named.
