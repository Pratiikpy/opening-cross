# Feature status

`PRODUCT_FEATURES.md` is the specification of the product: everything the company intends to build. This file says, row by row, what exists today. It was produced on 2026-10-12 by reading the program sources, the clients, services and apps, the ADRs and the evidence files; no test was run for it. Where a figure appears it comes from a file in `docs/evidence/` or from `docs/ROADMAP.md`.

**Status words**

- **BUILT**: working code on every layer that applies to the row, and a passing test or an evidence file that proves it.
- **PARTIAL**: some layers or some of the row's claims exist. The Gap column names exactly what is missing.
- **NOT BUILT**: no code. The reason is later roadmap, a counsel or partner dependency, or a human task (`docs/HUMAN_TASKS.md`).

IDs are the ones in `PRODUCT_FEATURES.md`. They are a different numbering from the ROADMAP's `A1`–`A5` and `C1`–`C6`, which are build items.

What is built, in one paragraph: five on-chain programs (`cross_core`, `cross_gate`, `cross_settle`, `cross_calendar`, `treasury`) deployed on devnet and equal to the local builds byte for byte; the clearing rule in `clearing-core` with an independent TypeScript verifier and 525 conformance vectors; four settlement adapters (Meteora DBC continuation, DAMM v2, DLMM, Raydium CPMM) each proved on devnet; identity gating with real SAS attestations; the ownership-coin treasury; an indexer, keepers, an API, an MCP server, a signed-promise track record and a premium monitor; and a web app and a native app. Rows still marked PARTIAL or NOT BUILT name their gap; the ones that need a program change are written and tested locally and wait on devnet funding (H27).

**Counts (2026-10-14):** 38 BUILT, 8 HUMAN, 82 PARTIAL, 20 NOT BUILT (one row is NOT MEASURED). The wave 2D rows (cross_core rules, treasury extension, cross_settle Meteora rows) are proved on LiteSVM against the real program binaries and are not deployed: the operator key needs about 11.1 SOL for the three upgrades (H27), then `sh scripts/deploy-batch-2.sh --execute` runs the upgrades, the hash check and the devnet proofs. They stay PARTIAL, not HUMAN, wherever an app layer is missing: the SDK has no builders for the new rules, the issuer console and API do not send or show them, the indexer, API and UI do not read the new treasury instructions, and indexer handling of the new cross_core events is NOT VERIFIED.

**Decisions awaiting founder confirmation** (each is recorded in an ADR and leaves the row NOT BUILT until confirmed or reversed):

- W12, B3 continuous-clearing mode: not part of `cross_core`; a separate program if ever built (`docs/adr/0458-*.md`).
- K4 governed treasury yield: not before an audit, because a yield CPI conflicts with always-liquid NAV redemption (`docs/adr/0476-*.md`).
- D6: not doing (`docs/adr/0486-*.md`).
