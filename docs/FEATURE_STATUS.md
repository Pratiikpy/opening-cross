# Feature status

`PRODUCT_FEATURES.md` is the specification of the product: everything the company intends to build. This file says, row by row, what exists today. It was produced on 2026-10-12 by reading the program sources, the clients, services and apps, the ADRs and the evidence files; no test was run for it. Where a figure appears it comes from a file in `docs/evidence/` or from `docs/ROADMAP.md`.

**Status words**

- **BUILT**: working code on every layer that applies to the row, and a passing test or an evidence file that proves it.
- **PARTIAL**: some layers or some of the row's claims exist. The Gap column names exactly what is missing.
- **NOT BUILT**: no code. The reason is later roadmap, a counsel or partner dependency, or a human task (`docs/HUMAN_TASKS.md`).

IDs are the ones in `PRODUCT_FEATURES.md`. They are a different numbering from the ROADMAP's `A1`–`A5` and `C1`–`C6`, which are build items.

What is built, in one paragraph: five on-chain programs (`cross_core`, `cross_gate`, `cross_settle`, `cross_calendar`, `treasury`) deployed on devnet and equal to the local builds byte for byte; the clearing rule in `clearing-core` with an independent TypeScript verifier and 525 conformance vectors; four settlement adapters (Meteora DBC continuation, DAMM v2, DLMM, Raydium CPMM) each proved on devnet; identity gating with real SAS attestations; the ownership-coin treasury; an indexer, keepers, an API, an MCP server, a signed-promise track record and a premium monitor; and a web app and a native app. Rows still marked PARTIAL or NOT BUILT name their gap; the ones that need a program change are written and tested locally and wait on devnet funding (H27, H43).

**Counts (2026-10-16, after waves 4A and 4B):** 39 BUILT, 32 HUMAN, 65 PARTIAL, 12 NOT BUILT (one row is NOT MEASURED); the count is of table rows, and many rows group several IDs. The programs of wave 2D (cross_core rules, treasury extension, cross_settle) and wave 3D (seven new programs: cross_mandate, cross_conviction, cross_basket, cross_listing, cross_bounty, cross_backing, cross_graduate; the fixed-price presale and MetaDAO paths in cross_settle; governed graduation in cross_core) are proved on LiteSVM against the real binaries and on a local validator, and none of it is deployed: batch 2 upgrades three programs (H27) and batch 3 deploys the seven new ones (H43), then the devnet proofs run. Waves 3A to 3C built the layers above the wave 2D programs (SDK builders and about 60 unsigned-transaction routes, indexer projections, verifier checks and proof v2, MCP tools, a keeper that builds the rules tail, the issuer rules step, treasury console and settle page, the holder rules read-out and treasury actions, receipt v2, and `GET /v1/programs`, which says which release is deployed so the web offers nothing the old programs would refuse). Wave 3E added the routes for every pool opening, Alpha Vault, Met Lock, fee sharing and the arbiter, and the keeper duties for pushed refunds, challenge expiry, lock release, series spawning and halts (opt-in where the keeper pays rent, `W3E-markets-keeper-neutrality.md`); wave 3F added the series, halt, arbiter, wind-down, dashboard and settle-opening screens (`W3F-screens.md`). A row is HUMAN only when every layer exists and the sole step left is H27 (plus any named counsel, attester, multisig or provider step); no new instruction has run on a cluster, because the browser runs decode the signed transactions in a harness and the indexer ran on PGlite. Waves 4A and 4B then built every layer above the seven new programs and the two new `cross_settle` instructions: SDK and client builders, release-gated routes (409 `PROGRAM_NOT_DEPLOYED` until the cluster has the program), indexer migration 019, MCP tools, keeper duties for graduation, backing, listings and bounties, the backing attester, and the web screens (`W4A-offchain-layers.md`, `W4B-screens.md`). Their rows are HUMAN (H27, H43) except X3 and B4, which stay PARTIAL because the indexer does not decode their events. Rows stay PARTIAL where a layer or a named part is missing: the allocation policies not built (B9), flipper priority (B12), buyback, exit and liquidation flows (Y1), the lender and tokenizer feeds (W11, Z3), and the Alpha Vault, DLMM fill and DAMM v2 or DBC stock-quote paths not covered (X13, X12).

**Decisions awaiting founder confirmation** (each is recorded in an ADR and leaves the row NOT BUILT until confirmed or reversed):

- W12, B3 continuous-clearing mode: not part of `cross_core`; a separate program if ever built (`docs/adr/0458-*.md`).
- K4 governed treasury yield: not before an audit, because a yield CPI conflicts with always-liquid NAV redemption (`docs/adr/0476-*.md`).
- D6: not doing (`docs/adr/0486-*.md`).
- D8 Zap: a zap is a client-built transaction, not a program (`docs/adr/0658-*.md`).
- X14, R1 volume engine and R4 multi-asset pairing: neither needs a program; the work is an indexer table, an API route and router changes (`docs/adr/0659-*.md`).
